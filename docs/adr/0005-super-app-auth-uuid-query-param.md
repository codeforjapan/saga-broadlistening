# ADR 0005: スーパーアプリ連携認証をUUIDクエリパラメータ方式にする

## ステータス

提案中

## 日付

2026-07-14

## コンテキスト

市民向け常設利用は「スーパーアプリ」経由での認証連携が前提となっており、実装方式としてトークン認証とUUIDのクエリパラメータ渡しの2案が検討されていた（Notion「佐賀広聴の仕組み Optimさん」メモ, 2026-07-10時点では暫定的にUUID方式を採用）。

## 決定

スーパーアプリからサーバーへのリクエスト時、ユーザーのUUIDをクエリパラメータに載せて渡す方式を採用する（トークン認証は行わない）。

## 根拠

- 実装のシンプルさ: トークン発行・検証のフローが不要。
- スケジュール: 8月実装開始に向け、スーパーアプリ側の連携仕様に沿った実装が容易。
- 機密性要件: UUIDの機密性はプロジェクト側で重視されていないことを2026-07-14に確認済み。

## 影響

### メリット

- 実装がシンプル
- 開発速度が上がる

### 懸念点

- クエリパラメータはアクセスログやRefererヘッダを通じて残る可能性がある
  - 緩和策: サーバーサイドのアクセスログでクエリパラメータをマスキングする。ログの保持期間を必要最小限にする。
- UIDが総当たり（ブルートフォース）で推測される可能性
  - 前提確認: このUIDが暗号論的に十分ランダムなUUID（例: UUIDv4、122bitのランダム性）なのか、市民証番号由来で桁数が少なく予測しやすいものなのかは未確認。前者なら総当たりは現実的に不可能（リスクの本質は発行済みUIDの漏洩の方になる）だが、後者なら総当たりは現実的な脅威になるため、Optim社への確認が必須。
  - 緩和策: (1) ALB/AWS WAFのレート制限（Rate-based rule）で同一IP・短時間あたりのリクエスト数を制限し連続試行を遅くする。(2) 未マッチのUIDに対して「該当なし」と明確に区別できるレスポンスを返さない（新規匿名ユーザーとして扱う等）ことで、攻撃者が推測の正解/不正解を判別できないようにする。(3) スーパーアプリのWebView以外からのアクセスを難しくするガード（WebViewビルドにのみ埋め込む固定APIキー/署名ヘッダの追加、Referer/User-Agent検証等）をOptim社と調整する。(4) 短時間に多数の異なるUIDを試すパターンをCloudWatch/Langfuse等で監視し、自動でIPブロック・アラートする。(5) UIDが当たった場合でも見える情報を本人の意見履歴程度に限定し、設定変更・退会などのより機微な操作はUIDだけでは行えないようにする。

## 代替案

トークンベース認証（スーパーアプリが発行した一時トークンをヘッダで渡す）。UUIDが直接露出しないメリットがあるが、実装・検証の手間が増え、スーパーアプリ側との仕様調整も必要になるため、スコープ・スケジュールを優先し不採用。

## 今後の方向性

将来的にUUIDの機密性要件が上がった場合、トークンベース認証への切替を再検討する。7月中の認証仕様確定までに、UIDのエントロピー・形式（暗号論的にランダムなUUIDか、予測しやすい市民証番号由来かなど）をOptim社に確認することを具体的な次のアクションとする。
