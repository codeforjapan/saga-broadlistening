# ADR 0005: スーパーアプリ連携認証をUUIDクエリパラメータ方式にする

## ステータス

採用（2026-10-06 に追記。UID の受け渡しはクエリパラメータから URL フラグメントへ変更）

## 日付

2026-07-14

## コンテキスト

市民向け常設利用は「スーパーアプリ」経由での認証連携が前提となっており、実装方式としてトークン認証とUUIDのクエリパラメータ渡しの2案が検討されていた（Notion「佐賀広聴の仕組み Optimさん」メモ, 2026-07-10時点では暫定的にUUID方式を採用）。

## 決定

スーパーアプリからサーバーへのリクエスト時、ユーザーのUUIDをクエリパラメータに載せて渡す方式を採用する（トークン認証は行わない）。

## 根拠

- 実装のシンプルさ: トークン発行・検証のフローが不要。
- スケジュール: 8月実装開始に向け、スーパーアプリ側の連携仕様に沿った実装が容易。
- 機密性要件: UUIDの機密性はプロジェクト側で重視されていないことを2026-07-14に確認済み。

## 影響

### メリット

- 実装がシンプル
- 開発速度が上がる

### 懸念点

- クエリパラメータはアクセスログやRefererヘッダを通じて残る可能性がある
  - 緩和策: サーバーサイドのアクセスログでクエリパラメータをマスキングする。ログの保持期間を必要最小限にする。
- UIDが総当たり（ブルートフォース）で推測される可能性
  - 前提確認: このUIDが暗号論的に十分ランダムなUUID（例: UUIDv4、122bitのランダム性）なのか、市民証番号由来で桁数が少なく予測しやすいものなのかは未確認。前者なら総当たりは現実的に不可能（リスクの本質は発行済みUIDの漏洩の方になる）だが、後者なら総当たりは現実的な脅威になるため、Optim社への確認が必須。
  - 緩和策: (1) ALB/AWS WAFのレート制限（Rate-based rule）で同一IP・短時間あたりのリクエスト数を制限し連続試行を遅くする。(2) 未マッチのUIDに対して「該当なし」と明確に区別できるレスポンスを返さない（新規匿名ユーザーとして扱う等）ことで、攻撃者が推測の正解/不正解を判別できないようにする。(3) スーパーアプリのWebView以外からのアクセスを難しくするガード（WebViewビルドにのみ埋め込む固定APIキー/署名ヘッダの追加、Referer/User-Agent検証等）をOptim社と調整する。(4) 短時間に多数の異なるUIDを試すパターンをCloudWatch/Langfuse等で監視し、自動でIPブロック・アラートする。(5) UIDが当たった場合でも見える情報を本人の意見履歴程度に限定し、設定変更・退会などのより機微な操作はUIDだけでは行えないようにする。

## 代替案

トークンベース認証（スーパーアプリが発行した一時トークンをヘッダで渡す）。UUIDが直接露出しないメリットがあるが、実装・検証の手間が増え、スーパーアプリ側との仕様調整も必要になるため、スコープ・スケジュールを優先し不採用。

## 今後の方向性

将来的にUUIDの機密性要件が上がった場合、トークンベース認証への切替を再検討する。7月中の認証仕様確定までに、UIDのエントロピー・形式（暗号論的にランダムなUUIDか、予測しやすい市民証番号由来かなど）をOptim社に確認することを具体的な次のアクションとする。

## 追記（2026-10-06、Epic #147）

### UID 渡しを維持する理由

- 厳密な市民認証は要求しない。スーパーアプリ側が UID を URL に載せて本アプリを開く現行案を維持し、外部側での署名や一時認証コードの発行は必須条件に含めない（Issue #147 コメント「修正方針（案）」、2026-10-03）。
- 本アプリはマイナンバーや本人確認情報を受け取らない。UID は属性データとの突合（今年度は 11 月・1 月の手動エクスポート）に使う照合キーとして平文で保存し、UID の受領を本人確認の証明とは扱わない。
- UID の偽装による回答や誤った紐付けが残ることは、今回の前提として受容する。

### 受け渡し方式：クエリパラメータではなく URL フラグメント（`#uid=`）

- 当初案の `?uid=` はサーバーに届くため、アクセスログ・Referer・分析ツールの URL 収集に残る。フラグメントはブラウザがサーバーへ送らないため、`#uid=` に変更した（2026-10-06、ユーザー決定）。パラメータ名 `uid` は暫定で、OPTiM と調整する。
- クライアントは最初の JS 実行時点（root layout のインラインスクリプト）でフラグメントを退避し、`history.replaceState` で URL から除去する。その後、Route Handler（`POST /api/external-identity`）へ送り、httpOnly / Secure / SameSite=Lax の Cookie（有効期限 1 年）に保存する。
- 残り得る経路：ブラウザの履歴・ブックマーク（除去前の URL を保存した場合）、スーパーアプリ側のログ、インラインスクリプトが動かない環境。GA は page_view に `location.href` を載せるが、スクリプトが先に除去するため通常は含まれない。
- WebView の POST（`#` も URL も使わず本文で渡す）が可能かは OPTiM への確認事項として引き継ぐ。

### 汎用的な外部ID設計

- 佐賀市スーパーアプリを「外部ID連携元」の一つとして扱う。保存先は `external_identities`（`provider_key` + `external_uid` で一意、`first_seen_at` / `last_seen_at`）。
- 連携元の表示名・案内 URL・UID の受け取り仕様はコード側のレジストリ（`packages/shared/src/external-identity/providers.ts`）で管理し、DB には `provider_key` だけを持つ。連携元を追加しても参加条件の enum は増やさない。
- 回答との関連は `interview_sessions.external_identity_id`。参加条件に関係なく、紐付きがあれば保存する（公開テーマの回答も突合対象になるため）。

### 会話のアクセス権の分離

- 外部IDと Supabase（匿名）ユーザーの紐付けは `external_identity_users` に保持し、同じ外部IDに複数のユーザー（ブラウザと WebView）が紐付くことを許容する。
- 会話の閲覧・操作権限は従来どおり `interview_sessions.user_id`（Supabase セッション）で判定する。UID の一致だけでは別セッションの過去の会話にアクセスさせない。Cookie 消失後の再訪では、紐付けは再作成できるが過去の会話は自動復元せず、新しい回答として開始する。
- 参加条件（テーマ単位の `participation_mode`）と会話の所有者は、別々の判定として実装する。
