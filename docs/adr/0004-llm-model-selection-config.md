# ADR 0004: LLMモデル選定を設定で切り替え可能にする

## ステータス

提案中

## 日付

2026-07-14

## コンテキスト

LLM（バックエンドは AWS Bedrock 経由で呼び出す）は今後新しいモデルが継続的に登場し、また用途（要約、対話、政策文書生成など）によって適したモデルが異なる可能性がある。単一モデルをコードにハードコードすると、モデルの追加・入れ替えのたびにコード変更・再デプロイが必要になる。

## 決定

LLMモデルをコードにハードコードせず、ユースケースごとに設定（モデルID）で切り替え可能な構成にする。

## 根拠

- 技術的考慮: Bedrock はリクエストごとにモデル ID を指定できるため、設定切り替えのみで対応可能。
- 将来の柔軟性: 新モデル登場時に再デプロイ不要。
- ユースケースごとの最適化: 要約用・対話用など用途ごとに異なるモデルを使い分けられる。

## 影響

### メリット

- 新モデルへの追従が容易
- ユースケースごとに最適なモデルを選べる
- コード変更なしで切替可能

### 懸念点

- 設定管理の複雑化（ユースケース×モデルのマッピングが増えると管理コストが上がる）
  - 緩和策: 設定はDBまたは環境変数で一元管理し、変更履歴を追えるようにする。モデル追加時の検証（回帰テスト等）プロセスを整備する。
- 意図しないモデルが使用されるリスク（クライアントからの入力やAPI呼び出し経由で、想定していないモデルが指定・実行されてしまう）
  - 緩和策: (1) APIがクライアントから直接モデル名を受け取らない設計にする——外部/クライアントからのリクエストは「ユースケース名」（chat/summary等）のみを受け取り、実際のモデルIDへの変換はサーバー内部のマッピングだけが持つようにする（mirai-gikaiの`packages/shared/src/ai/models.ts`の`AI_MODELS`定数オブジェクトのように、呼び出し側は生の文字列ではなく定数キーを参照する設計を踏襲する）。(2) 管理画面等でモデルを選択させる場合もドロップダウン等の固定リストに限定し（`admin/src/features/interview-config/.../chat-model-options.ts`が既にこの形）、クライアント側の制限だけに依存せずサーバー側でも同じ許可リストと照合するバリデーションを必ず入れる。(3) 未知・非許可のモデル値が来た場合は黙って別のモデルにフォールバックせず、明確にエラーとするfail-closed設計にする。(4) `cost-tracker.ts`/`system-cost-guard.ts`のコストガードをモデル許可リストと併用し、想定外に高コストなモデルが選ばれた場合もコスト上限で検知・遮断できるようにする。(5) Langfuseのトレースに残る使用モデル情報を使って、意図した通りのモデルが使われたかを事後的に監査できるようにする。

## 代替案

単一モデルをコードにハードコードする。実装がシンプルというメリットがあるが、モデル追従性が低くユースケースごとの最適化ができないため不採用。
