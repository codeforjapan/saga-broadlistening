# AIインタビューのプロンプト生成ロジック

AIインタビューで LLM に渡すプロンプトを、**何を材料（シード値）にして**、**どの順でどう組み立てているか**をまとめる。2026-10-11 時点の `develop` のコードをもとに書いている。

## 1. 全体像

プロンプトは、管理画面で作った**設定（材料）**と、実行時に算出する**状態**を、**テンプレート**に差し込んで作る。

```
[admin] 意見募集の設定                      [DB] 公開中プロンプト（ai_prompts）
  ├ 施策（bill + 難易度別コンテンツ + 知識ソース）        │ なければ／不正ならソースコード既定
  ├ テーマ名・説明（interview_configs）                   ▼
  └ 事前定義質問（質問文・フォローアップ指針・選択肢）  テンプレート（{{変数}} 入り）
              │                                         │
              ▼                                         ▼
[web] 実行時の状態 ──► buildLoopModeSystemPrompt / buildSummarySystemPrompt
  ├ 現在ステージ（chat / summary / summary_complete）
  ├ 聞き終えた質問ID（会話履歴の question_id から収集）
  ├ 残り目安時間
  └ 会話履歴（summary のときのみ）
              │
              ▼
        システムプロンプト ──► LLM（構造化出力）──► text / quick_replies / question_id / topic_title / next_stage
```

LLM 呼び出しは3種類あり、それぞれ使うプロンプトが違う。

| 呼び出し | タイミング | プロンプト | 実装 |
| --- | --- | --- | --- |
| 初回質問 | セッション開始時（会話履歴なし） | 対話用プロンプト ＋ 開始指示 | `web/src/features/interview-session/server/services/generate-initial-question.ts` |
| 対話 | `chat` ステージの各ターン | 対話用プロンプト | `web/src/features/interview-session/server/services/handle-interview-chat-request.ts` |
| 要約・レポート | `summary` ステージの各ターン | 要約用プロンプト | 同上 |

プロンプトを組み立てるコードは `packages/shared/src/interview-prompts/` にまとめてあり、web の本番処理と admin のインタビューシミュレータが同じものを使う。

| ファイル | 役割 |
| --- | --- |
| `templates.ts` | 対話用・要約用テンプレートの既定本文 |
| `published.ts` | DB の公開版テンプレートを取得して組み立て関数に渡す |
| `loop-mode.ts` | 対話用プロンプトの組み立て（`buildLoopModeSystemPrompt`） |
| `summary.ts` | 要約用プロンプトの組み立て（`buildSummarySystemPrompt`） |
| `subject-section.ts` | 「施策型」と「テーマ型」で切り替わる断片、開始ターンの指示 |
| `stage-transition-guidance.ts` | ステージ遷移の判定ルール、残り時間の指示 |
| `bill-clarification-guidance.ts` | 施策の誤解を補足するための指示 |
| `chat-text-description.ts` | 出力スキーマの `text` フィールドの説明 |

## 2. 材料（シード値）

### 2.1 管理画面で設定するもの

| 材料 | 保存先 | プロンプトでの使われ方 |
| --- | --- | --- |
| 施策名 | `bill.name` | 「施策に関する知識」セクション |
| 施策タイトル・要約・本文 | `bill_content`（難易度別） | 同上。本文は `<bill_detail>` タグで囲む |
| 知識ソース | `bill.knowledge_source` | `<knowledge_source>` タグで囲む。未設定なら「（知識ソース未設定）」 |
| テーマ名 | `interview_configs.name` | 施策のない「テーマ型」で対象名として使う |
| テーマ説明 | `interview_configs.description` | 「インタビューテーマ」セクション。未設定なら「（テーマ未設定）」 |
| 事前定義質問 | `interview_questions` | 質問一覧、進捗の一覧 |
| 目安時間 | `interview_configs.estimated_duration` | 残り時間の計算 |
| 対話モデル | `interview_configs.chat_model` | 対話・初回質問で使うモデル（未設定なら既定のモデル） |

施策の本文には、**利用者が選んでいる難易度**（Cookie）の `bill_content` を使う（`web/src/features/bills/server/loaders/get-bill-by-id.ts`）。プレビューでは、未公開の施策も読める管理者用ローダーを使う。

どの施策を載せるかは、クライアントからは指定させない。意見募集IDから、紐づく施策をサーバー側で引く（`resolve-interview-chat-context.ts`）。無関係な施策の本文がプロンプトに混ざらないようにするためである。

### 2.2 事前定義質問の作られ方

事前定義質問も、admin の設定支援 AI が下書きを作る（`admin/src/features/interview-config/server/utils/build-config-generation-prompt.ts`）。

- **default_questions**: 7問の固定テンプレート（`default-questions-template.ts`）を使う。AI が作るのは Q1（関心のある論点）と Q2（立場）の選択肢だけで、質問文とフォローアップ指針は固定。
  - Q1 論点の選択 / Q2 立場の選択 / Q3 施策をどの程度知っているか / Q4 全体の評価 / Q5 Q1 の論点の深掘り / Q6 運用上のハードル / Q7 制度を設計する人へ伝えたいこと
- **question_proposal**: 職員との対話で質問をブラッシュアップする。フォローアップ指針の深さは、施策型では「1往復まで」、テーマ型では「2〜3往復まで」と指示を変える。
- **theme_proposal**: 確定した質問をもとに、分析用のテーマ（ラベル）を提案する。

ここで確定した `question` / `follow_up_guide` / `quick_replies` が、インタビュー本番のプロンプトにそのまま入る。

### 2.3 実行時に算出するもの

| 値 | 算出方法 |
| --- | --- |
| `currentStage` | クライアントが送ってくる現在のステージ |
| `askedQuestionIds` | DB の会話履歴のうち、assistant メッセージの JSON から `question_id` を集めたもの（`collect-asked-question-ids.ts`） |
| `remainingMinutes` | `estimated_duration − (現在時刻 − セッション開始時刻)` を分単位に切り上げ、0 未満は 0。`estimated_duration` 未設定なら `null` |
| `nextQuestionId` | 都度深掘りモードでは常に `undefined`。次にどの質問をするかは LLM に任せる（`loop-mode.ts` の `calculateLoopModeNextQuestionId`） |
| 会話履歴 | summary ステージでのみプロンプトに埋め込む。user の発言には DB のメッセージIDを付ける |

## 3. テンプレートの取得

テンプレートは管理画面の「AIプロンプト」から編集・公開できる。対象のキーは次の2つ。

| キー | 名前 | 必須変数 |
| --- | --- | --- |
| `interview-chat-system` | AIインタビュー・対話方針 | `focusInstruction` `clarificationGuidance` `knowledgeSection` `themeDescription` `questionsText` `replyExamples` `perspectiveTechniques` `stopPolicy` `stopSigns` `stopFollowUps` `outputInstructions` |
| `interview-summary-system` | AIインタビュー・要約方針 | `summarySection` `themeDescription` `conversationLog` `reportInstructions` |

取得の流れは次のとおり（`packages/shared/src/prompts/provider.ts` の `PromptProvider.getTemplate`）。

1. `ai_prompts` から公開中バージョン（`published_version_id`）の本文を取得する。タイムアウトは2秒。
2. 次のどれかに当たる場合は、ソースコードの既定本文（`templates.ts`）を使う。
   - 取得でエラーになった
   - 公開版がない
   - 検証に失敗した（必須変数がない、同じ変数が2回以上ある、未知の変数がある、括弧が不正）
3. 既定本文に切り替えたときは `Interview prompt fallback` を警告ログに出す。

`{{変数名}}` の置換は `renderPromptTemplate`（`packages/shared/src/prompts/template.ts`）が行う。必須変数を渡し忘れると例外になる。

**編集できる範囲**: テンプレートで編集できるのは、変数のまわりの固定文（口調、注意事項、深掘りの方針など）だけ。変数に入る中身（施策情報、質問一覧、出力の指示、ステージ遷移の判定ルールなど）はコードで組み立てるので、管理画面からは変えられない。

## 4. 対話用プロンプト（`interview-chat-system`）

`buildLoopModeSystemPrompt`（`packages/shared/src/interview-prompts/loop-mode.ts`）が組み立てる。

### 4.1 テンプレートの構成

既定テンプレートは、次の順に並んでいる（`{{ }}` は差し込まれる変数）。

1. インタビュアーとしての役割と責任
2. 注意事項（1メッセージ1論点、「なぜ」を多用しない、など）＋ `{{focusInstruction}}`
3. `{{clarificationGuidance}}`（施策の誤解への補足）
4. `{{knowledgeSection}}`（施策の知識、またはテーマの説明）
5. インタビューテーマ: `{{themeDescription}}`
6. 専門知識レベルの見極め（初心者・中級・専門家）
7. 事前定義質問: `{{questionsText}}`
8. 都度深掘りモード（Loop Mode）の方針
9. 返答の組み立て方（受け止め → 質問1つ、書く前の5つの確認）＋ `{{replyExamples}}`
10. 話題の移り方
11. 深掘りのテクニック ＋ `{{perspectiveTechniques}}`
12. 深掘りをやめる基準: `{{stopPolicy}}` `{{stopSigns}}` `{{stopFollowUps}}`
13. 事前定義質問の使い方と終了の判定
14. `{{outputInstructions}}`（残り時間・出力フィールド・ステージ遷移）

### 4.2 施策型とテーマ型の切り替え

`buildInterviewSubject`（`subject-section.ts`）が、**施策があるか（`bill` が null でないか）**で断片を切り替える。テーマ型（抽象テーマ型の意見募集）には施策の資料がない。施策の欄を空欄のまま並べると、AI が存在しない施策を語り出すため、断片ごと差し替えている。

| 変数 | 施策型（bill あり） | テーマ型（bill なし） |
| --- | --- | --- |
| `knowledgeSection` | 「施策に関する知識」: 施策名・タイトル・要約・`<bill_detail>`・`<knowledge_source>` | 「インタビューの対象」: テーマ名と「施策の資料はない。存在しない制度を推測しない」という注意 |
| `focusInstruction` | 施策に関する質問だけに集中する | テーマに関する質問だけに集中する |
| `clarificationGuidance` | 施策の誤解に気づいたら補足する（`BILL_CLARIFICATION_GUIDANCE`） | 空 |
| `perspectiveTechniques` | 施策が実施されたら／されなかったら。賛成の人に懸念を聞く | 「もし○○が身近にあったら」。不便さを話した人に良い点を聞く |
| `stopPolicy` | 施策への意見づくりに役立つところで止める | 日常のエピソードや気持ちそのものが集めたい情報なので、打ち切らずに掘り下げる |
| `stopSigns` | 施策の論点から離れた／一般化できない／具体例を1〜2個得た | 答えが出てこない／同じ話の繰り返し／十分に聞けた |
| `stopFollowUps` | 別の角度へ広げる／施策の制度の話に戻す | 関わる人・時間帯・お金・場所など別の角度から聞く |
| `replyExamples` | 給食費を題材にした良い例・悪い例 | 暮らしのテーマで実際に起きた失敗（複数質問・聞き直し）を例にしたもの |

### 4.3 質問一覧（`questionsText`）

事前定義質問を、次の形式で番号付きに並べる。

```
1. [ID: q1] この施策についてどう思いますか？
   フォローアップ指針: 賛成・反対の理由を深掘りする
2. [ID: q2] 業務への影響はありますか？
   クイックリプライ: はい, いいえ, わからない
```

フォローアップ指針と選択肢は、設定されている場合だけ付ける。質問が1件もなければ「（賛成か、反対か）」を入れる。

### 4.4 出力の指示（`outputInstructions`）

コードで組み立てる部分で、次の4つをつなげたもの。

1. **残り時間の指示**（`buildTimeManagementGuidance`）
   - `remainingMinutes` が `null` なら何も出さない
   - 1分以上残っていれば「残り約N分・残りM問。時間と質問数のバランスを見る」
   - 0分（超過）なら「ユーザーがレポート作成に進みたいと言ったら summary に。続けたいなら通常どおり深掘り」
2. **クイックリプライの指示**: 事前定義質問をするときは `question_id` と、設定されていれば `quick_replies` を出す。深掘り質問では `question_id` を null にする。選択を促す質問では必ず `quick_replies` を出す。
3. **トピックタイトルの指示**: 事前定義質問をするときは `topic_title` を20文字以内で出す。それ以外は null。
4. **ステージ遷移の判定**（`buildLoopModeStageGuidance`）: 現在のステージに応じたルールと、質問の進捗。
   - `chat`: 事前定義質問を概ね終え、十分に深掘りしたら `summary` を検討する。ユーザーが終了を望んだときや、これ以上の深掘りが難しいときも `summary`。消化を急がず、各テーマで2〜3回のフォローアップを優先する。
   - `summary`: ユーザーが同意したら `summary_complete`、直しが続くなら `summary`、再開を望んだら `chat`。
   - `summary_complete`: `summary_complete` のまま。
   - 進捗: 「N問中M問完了（残りK問）」と、完了した質問・まだ聞いていない質問の一覧。完了の判定には `askedQuestionIds` を使う。

### 4.5 初回質問だけに足す指示

初回は会話履歴がないので、対話用プロンプトの末尾に `buildInitialTurnInstruction` の文を足し、`generateText` の `prompt` として渡す。

- 2文ほどの温かい挨拶で、「（対象名）」についてのインタビューだと伝え、すぐ最初の事前定義質問をする
- 対象名（`resolveSubjectTitle`）は、施策タイトル → 施策名 → テーマ名 → 「このテーマ」の順で、最初に値があるものを使う
- 最初の質問のIDを `question_id` に入れる。選択肢があれば `quick_replies` に入れる

生成後、`topic_title` は「はじめに」に上書きしてから保存する（`override-initial-topic-title.ts`）。

### 4.6 モデルに渡すメッセージ

- system: 組み立てたシステムプロンプト
- messages: クライアントから届いた会話履歴。末尾が assistant のとき（summary から chat に戻った直後など）は、末尾に「続けてください。」という user メッセージを足す。Anthropic 系のモデルは会話が user で終わる必要があるためで、足したメッセージは DB に保存しない（`ensure-trailing-user-message.ts`）。
- 出力スキーマ: `interviewChatTextSchema`（`text` / `quick_replies` / `question_id` / `topic_title` / `next_stage`）。`text` の説明（`INTERVIEW_CHAT_TEXT_DESCRIPTION`）にも「受け止めを1〜2文、質問は1つ、『？』は1回まで」と書いてある。gpt-oss は構造化出力をツール呼び出しで返すため、本文より書く直前に読むこの説明のほうが効くからである。

## 5. 要約用プロンプト（`interview-summary-system`）

`currentStage === "summary"` のとき、`buildSummarySystemPrompt`（`packages/shared/src/interview-prompts/summary.ts`）で組み立てる。

| 変数 | 中身 |
| --- | --- |
| `summarySection` | 施策型: 施策名・タイトル・要約（本文と知識ソースは入れない）。テーマ型: テーマ名と説明 |
| `themeDescription` | テーマ説明。未設定なら「（テーマ未設定）」 |
| `conversationLog` | 会話全体を `role: 内容` の形で1行ずつ並べたもの。user の発言は `user [msg_id:UUID]: 内容` として DB のメッセージIDを付ける（`merge-messages-with-ids.ts` で紐づける） |
| `reportInstructions` | レポートの各フィールドの書き方と、ステージ遷移の判定 |

`reportInstructions` で指示している主な内容は次のとおり。

- `summary`: 100文字ほどの、話し言葉に近いやわらかい要約
- `final_text`: 本人がそのまま提出できる300文字ほどの意見文。インタビュアーの発言を本人の意見として書かない
- `role_description` / `role_title`: 立場。過去の経歴は「元〜」と書き、今の立場と区別する。`role_title` は10文字以内
- `opinions`（最大3件）: 施策を検討する人にとって役立つ順に並べる。根拠はユーザーの発言だけで、本人が言っていない要望や賛否に格上げしない。`source_message_id` に根拠の msg_id、`contextual_quote` にその発言からの逐語引用（固有名詞は入れない）、`richness`（0〜100）、`concern` / `proposal` / `reasoning_types` のタグ
- 情報の充実度の評価（`buildContentRichnessInstructions`）
- `next_stage`: レポートを出して確認を待つなら `summary`、同意を得たら `summary_complete`、再開を望んだら `chat`（このとき `report` は出さず、次の質問を1つ出す）

モデルに渡すメッセージは**末尾の user メッセージ1件だけ**にする。会話全体はすでにシステムプロンプトに入っているので、二重に送らないためである。末尾が user でない場合（chat から summary へ自動で移ったときなど）は、「ここまでの会話内容をもとに、インタビューのレポートを作成してください。」という user メッセージを足す。このメッセージも DB には保存しない（`build-summary-model-messages.ts`）。出力スキーマは `interviewChatWithReportSchema`（`text` / `report` / `next_stage`）。

## 6. 1ターンの処理の流れ

`handleInterviewChatRequest` の処理順。

1. 次の3つを並列で行う: 1日あたりのコスト上限の確認、意見募集と施策の解決、外部IDの読み込み
2. 参加条件を判定する（プレビューでは判定しない）
3. 次の2つを並列で行う
   - 事前定義質問の取得
   - セッションの取得（なければ作成）→ ユーザーの発言を保存 → DB から会話履歴を取得
4. 会話履歴から `askedQuestionIds` を集め、`remainingMinutes` を計算する
5. ステージに応じて、対話用か要約用のプロンプトを組み立てる（その中で DB から公開版テンプレートを取る）
6. `streamText` で構造化出力をストリーミングで返す。終わったら assistant の発言を保存し、利用コストを記録する

`next_stage` は、対話している LLM 自身が出力する。進行を判断する LLM を別に呼ぶことはしない。

## 7. 関連する仕組み

- **インタビューシミュレータ**（`admin/src/features/interview-simulation/`）: インタビュアー役には、本番と同じ `buildPublishedInterviewPrompt`（公開版テンプレート ＋ `buildLoopModeSystemPrompt`）と `buildInitialTurnInstruction` を使う。回答者役（ペルソナ）のプロンプトは別に組み立てる。
- **テスト**: 組み立ての挙動は `packages/shared/src/interview-prompts/loop-mode.test.ts`、`subject-section.test.ts`、`web/src/features/interview-session/shared/utils/interview-logic/loop-mode.test.ts` などで確認している。テンプレートを変えるときは、これらのテストで含まれるべき文言を確かめる。
- **Bulk Mode（一括回答優先モード）**: `buildBulkModeStageGuidance` が残っているが、本番のプロンプトでは使っていない（都度深掘りモードのみ）。
