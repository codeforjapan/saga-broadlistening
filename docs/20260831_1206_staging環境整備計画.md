# develop環境（staging）整備計画

develop環境（staging）を本格的に整えるにあたっての現状調査・未整備箇所・手順のまとめ。

## 現状（すでにできていること）

### Supabase + Vercel のデプロイパイプラインは既に稼働中

- `.github/workflows/deploy.yml`は`develop`へのpushで`staging` GitHub Environmentを使い、Supabase migrate → Vercel Deploy Hook起動、まで動く
- `staging`環境のSecretsは必要な8種類（`SUPABASE_ACCESS_TOKEN` / `SUPABASE_PROJECT_REF` / `SUPABASE_DB_PASSWORD` / `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID` / `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET` / `ADMIN_AUTH_CALLBACK_URL` / `WEB_VERCEL_DEPLOY_HOOK_URL` / `ADMIN_VERCEL_DEPLOY_HOOK_URL`）が揃っている
- 直近の実行ログでは直近2回成功（2026-08-31）。それより前は`Supabase link`ステップの失敗が数回あるが、一時的なものと思われる
- `web/vercel.json`・`admin/vercel.json`で`develop`ブランチの自動デプロイを明示的に無効化し（`git.deploymentEnabled.develop: false`）、Deploy Hook経由でのみデプロイする設計になっている（DBマイグレーション成功後にのみアプリがデプロイされる順序保証のため）

### 気になった点（要クリーンアップ）

- `staging`環境のSecretsに`SUPABASE_DB_PASSWORD`と、タイプミスと思われる`SUPBASE_DB_PASSWORD`（Aが抜けている）の**両方**が登録されている。正しい方が存在するので動作に支障はなさそうだが、紛らわしいので削除しておくのが望ましい

## 未整備（ここが「develop環境を整える」の本丸）

### AWS側のインフラがstg環境に一切存在しない

- `infra/aws-cdk/lib/config/environments/stg.ts`が`UNCONFIGURED_ACCOUNT_ID`（プレースホルダー）のままで、`resolveEnvConfig()`はこの値だと例外を投げる仕組みになっている
- `CDK Deploy [prd]` / `CDK Diff [prd]` ワークフロー（`cdk_deploy.yml`, `cdk_diff.yml`）は**`main`ブランチ限定**。stg向けの同等ワークフローは存在しない
- `Deploy Topic Analysis Worker (ECR)`ワークフロー（`deploy_worker_ecs.yml`）も**`main`限定**。stg用のworkerイメージpushは無い
- GitHub `staging`環境のSecretsにも、prd環境にある`AWS_CDK_PRD_DEPLOY_ROLE_ARN`に相当するものが**無い**

つまり、Bedrock呼び出し・トピック分析worker（AWS Batch）・adminからの手動実行トリガは、stg環境では今のところ動かない状態のはず（AWS Batch用のJob Queue/Job Definition ARN自体が存在しないため）。

## 手順（この順番で進める）

1. **AWSアカウントを用意する**: stg用に独立したAWSアカウントを使うか、devアカウントを流用するか方針を決める（`stg.ts`の`account`に実IDを入れる）
2. **CDKスタックをstgにデプロイする**: `infra/aws-cdk/README.md`の手順に沿って`cdk bootstrap` → 初回`cdk deploy --context env=stg`を手動実行（OIDCロールが無い状態なので最初は手動）
3. **GitHub OIDCデプロイロールを払い出す**: `MiraiGikaiGitHubOidcStack-stg`が作るロールのARNを、`staging`環境のSecretに`AWS_CDK_STG_DEPLOY_ROLE_ARN`のような名前で登録
4. **CDK Deploy/Diffワークフローをstg対応にする**: `cdk_deploy.yml`/`cdk_diff.yml`を参考に、`develop`ブランチ向けの並行ワークフロー（`environment: staging`, `context_env: stg`）を追加
5. **workerイメージをstg用ECRにpush**: 初回は手動、その後`deploy_worker_ecs.yml`を参考にstg向けjobを追加（今のOIDCロール信頼条件が`main`限定なので、`develop`も許可するよう修正が必要）
6. **Vercel側の環境変数をstg用に設定**: admin/webそれぞれのVercelプロジェクトの`Preview`(develop用)環境に、`AWS_ROLE_ARN` / `TOPIC_ANALYSIS_BATCH_JOB_QUEUE_ARN` / `TOPIC_ANALYSIS_BATCH_JOB_DEFINITION_ARN` / `AWS_REGION`をstgスタックの出力値で設定
7. **EventBridge Schedulerの扱いを決める**: stgで定期実行させるか（`topicAnalysisSchedulerEnabled`）、手動実行のみにするか

## 確認したい情報

- stg用に**新規AWSアカウントを作る**か、**devアカウントと共用**するか
- GCP側（旧実装）はstg環境で今どうなっているか（Cloud Run Job/Schedulerがまだ動いている？停止済み？）— これによって「二重実行防止」の要否が変わる
- staging用のドメイン/URLの希望（Vercelの`develop`ブランチ自動生成URLのままでよいか、`staging.mirai-gikai.org`的な独自ドメインを用意するか）
- stgでBedrock Guardrails・モデルアクセスのAWSコンソール手動有効化（`docs`に「モデル自体の有効化はコード管理対象外」と明記あり）を誰が行うか
