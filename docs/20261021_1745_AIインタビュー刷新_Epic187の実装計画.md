# AIインタビュー刷新（Epic #187）の実装計画

PR #164 で試作した AIインタビューの刷新を、子 Issue（#188〜#202）ごとの PR に分けて develop の上に作り直す。この文書は PR の分け方と、着手前に決めた事項をまとめる。仕様の値（発話の上限など）は Epic と各 Issue、および PR #164 の最終形のコードを正とする。

## PR の分け方

PR は Issue ごとに1本ずつ作る。stack は2つに分ける。

### stack A: develop に直接出す

DB を変えず、develop で今起きている不具合を含むので、統合ブランチを通さない。

1. #201 AI設定生成の不具合修正
2. #202 作成・編集画面を `/interviews` 配下に一本化

#202 と #196 はどちらも `interview-config-form.tsx` を大きく直す。#196 に着手する前に、#202 を `feat/interview-v2` の履歴に取り込む（develop へのマージ後に develop を取り込む）。

### stack B: 統合ブランチ `feat/interview-v2` に積む

`feat/interview-v2` は origin/develop から作る。下から順に積み、すべてそろったら `feat/interview-v2 → develop` の PR を1本出す。

1. #188 DB スキーマ（この PR。設計文書を含む）
2. #189 目的5型のテンプレートとシード
3. #190 対話のターン制御（shared の純粋関数）
4. #191 要約・再開のターン制御（shared の純粋関数）
5. #192 プロンプトの刷新
6. #193 web のチャット API をサーバー側のターン制御に切り替え
7. #194 web のチャット画面
8. #195 関連施策をプロンプトに載せる
9. #196 admin の設定項目（目的など）と「観点」への表記変更
10. #197 「目的のテンプレートを適用」
11. #198 admin のプロンプト管理
12. #199 シミュレータを本番と同じターン制御に
13. #200 AI設定生成に設計を渡す

統合ブランチを使う理由: #192 でプロンプトの必須変数と出力スキーマが変わるので、web・admin の呼び出し側は、コンパイルが通るだけの最小限の変更にとどめる。ステージ判定・ストリーム・保存を本当に切り替えるのは #193 になる。develop に直接積むと、#193・#194 が入るまでのあいだ、本番で新しいプロンプトと古い制御が混ざってしまう。

`Resolves #xxx` は、PR がデフォルトブランチ（develop）にマージされたときにしか Issue を閉じない。stack B の各 PR にも書いておくが、Issue が閉じるのは最後の `feat/interview-v2 → develop` の PR のマージ時（または手動）になる。

## 決定事項

### スキーマ（#188）

- 提出時（`completed_at` を入れるとき）は、同じ更新で `stage` も `summary_complete` にする（#193）
- 既存データの埋め方: 要約のあとインタビューに戻った未完了のセッションは、最後の assistant の発話がレポートではないので `chat` のままにする
- 再開の話題の発話は `question_id: "resume"` で保存する。`extract_assistant_question_id` は UUID でない値に NULL を返すので、`get_question_answer_counts` の集計からは外れる。どの質問にも当たらない発話なので、これでよい

### ターン制御（#190・#191）

- 発話の上限は「質問の数 × 10」、話題ごとの発話は目安5回（Epic の決定事項）
- `question_id` を持たない古い発話は、全体の上限だけを消費し、話題ごとの回数には数えない
- 要約からの再開は1回まで。再開の話題の上限は2回で、再開を受けた発話も1回に数える。要約の段階の発話は通算5回まで

### プロンプト（#192）

- 「佐賀市」はテンプレートと人物像に直書きのまま残す。自治体名の設定は develop にない。中立化は PR #115 で扱う
- 資料にないことを聞かれたときの案内: 主たる施策の担当課（`policies.department`）を対話方針に渡す
  - 担当課があるとき:「その点はこのインタビューではお答えできません。施策紹介ページや〇〇で確認できます」
  - 担当課がないとき: 施策紹介ページだけを案内する
- 必須変数が合わない旧公開版は、`PromptProvider` の invalid の扱いでソースの初期文面に戻る。admin に「無効」の表示は足さない（下の「運用作業」を参照）

### web（#193・#194）

- `SkipActionPopover` は削除する。「次の質問に進む」は「この質問はとばす」、「インタビューを終了する」は常設の「終える」と役割が重なる
- 開始画面（#158）の案内に「聞き手がAIであること」「いただいた声は、市の施策に役立てます」を1行ずつ足す。初回の発話は120字以内なので、そこには入れない
- 「終える」の確認: 対話中は確認なしで押せる（要約のあとに1回戻れるため）。要約中は完了して戻れないので確認を出す

### 関連施策（#195）

- 親施策も含め、紐づけの順に最大5件まで載せる。本文には長さの上限を置く

### admin（#196〜#200）

- 質問が0件の意見募集は公開できない。公開状態で保存するときに検証してエラーにする（#196）
- 「決まっていること」の欄は常に表示し、「施策に紐づく意見募集のときだけ使います」と説明を添える。テーマ型のときもプロンプトには渡さないが、値は消さない（#196）
- シミュレータ（#199）と「目的のテンプレートを適用」（#197）は、保存済みの目的を使う
- 「先頭の施策」の決め方は経路ごとにそろえず、現状のまま残す（AI設定生成とプレビューはフォームの順、シミュレータとプロンプト管理のプレビューは DB の順、web は公開済みの先頭）
- AI設定生成の新規生成（`default_questions`）の7問テンプレートは変えない（Epic の対象外）。観点の「最大3往復」も残す

### stack A（#201・#202）

- Slug は、新規作成時に自動で初期値を入れ、編集もできるようにする
- 「紐づく施策」には親施策も選べる。プレビューは従来どおり「その施策の募集中（なければ最新）の意見募集」を開く

### シード（#189）

- 若者支援は「見つける×テーマ」、高齢者支援は「わかる×テーマ」にする

## 運用作業

- 本番・ステージングにインタビューのプロンプトの公開版がある場合、#192 で必須変数が変わるので、旧版は検証で invalid になり、ソースの初期文面に自動で戻る。リリース後に管理画面で新しい文面を確認し、公開し直す
- 人物像（`interview-persona`）と初回の発話（`interview-initial-system`）は、この PR のマイグレーションで `ai_prompts` に登録する。版はまだないので、#192 が入るまではソースの初期文面が使われる
