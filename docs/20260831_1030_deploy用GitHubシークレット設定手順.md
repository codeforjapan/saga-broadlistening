# deploy 用 GitHub シークレット設定手順（staging environment）

## 背景

`develop` への push で走る `.github/workflows/deploy.yml`（Migrate DB then Deploy）が
`Supabase link` ステップで必ず失敗していた（run 32942174353 / 33347168191）。

```
Missing value for flag --project-ref. Expected: string
Missing value for flag --password. Expected: string
```

原因は staging environment にシークレットが1件も登録されていないこと。
`deploy.yml` は push 先のブランチで environment を切り替えるため、`main` だけが成功していた。

| ブランチ | environment | 状態 |
| --- | --- | --- |
| `main` | `production` | 登録済み → 成功 |
| `develop` | `staging` | 0件 → `supabase link` で失敗 |

シークレットの値はリポジトリ設定側にしか置けないため、この文書には
**何を・どこから取得して・どう登録するか** だけを記録する。

## 登録先

GitHub → リポジトリ `codeforjapan/saga-broadlistening` →
[Settings → Environments](https://github.com/codeforjapan/saga-broadlistening/settings/environments)
→ `staging` → Environment secrets

environment 名は `deploy.yml` / `supabase_preview.yml` が参照している `staging`（小文字）を使うこと。

なお本プロジェクトは Supabase Branching を使っており、`develop` に対応する DB は
親プロジェクト配下の **`develop` という名前のブランチ**（`staging` ではない）。
GitHub の environment 名と Supabase のブランチ名が一致しない点に注意する。
親プロジェクトの ref は `supabase projects list` で `saga-broadlistening` を探す。

## 必須シークレット（deploy.yml）

この8件が揃わないと `develop` の deploy は成功しない。`deploy.yml` の
`Check required secrets` ステップが冒頭で空チェックし、不足キーを列挙して失敗する。

このチェックは environment を問わず走るため、`production` 側にも同じ8件が必要になる。
本ドキュメント作成時点では `production` は8件すべて登録済みであることを確認済み
（`gh api repos/codeforjapan/saga-broadlistening/environments/Production/secrets --jq '.secrets[].name'`）。

| キー | 用途 | 取得元 |
| --- | --- | --- |
| `SUPABASE_ACCESS_TOKEN` | Supabase CLI の認証 | Supabase ダッシュボード → Account → Access Tokens |
| `SUPABASE_PROJECT_REF` | `supabase link` の接続先。**`develop` に対応する Supabase ブランチの ref**（親プロジェクトの ref ではない） | `supabase branches list --project-ref <親プロジェクトの ref> -o json` の `git_branch == "develop"` の `project_ref` |
| `SUPABASE_DB_PASSWORD` | `supabase link` の DB パスワード | `supabase branches get develop --project-ref <親プロジェクトの ref> -o env` が返す `POSTGRES_URL` に埋め込まれたパスワード部分 |
| `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID` | `supabase config push` が `config.toml` の `env()` を解決するのに必要 | [adminGoogleログイン設定手順](20260407_1800_adminGoogleログイン設定手順.md) の「2. OAuth クライアント ID の作成」 |
| `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET` | 同上 | 同上 |
| `ADMIN_AUTH_CALLBACK_URL` | 同上（admin のコールバック URL を許可リストに入れる） | 同上の「3. 環境変数の設定 → staging / production」 |
| `WEB_VERCEL_DEPLOY_HOOK_URL` | web の Vercel デプロイ起動 | Vercel → web プロジェクト → Settings → Git → Deploy Hooks（`develop` ブランチ向けに作成） |
| `ADMIN_VERCEL_DEPLOY_HOOK_URL` | admin の Vercel デプロイ起動 | Vercel → admin プロジェクト → Settings → Git → Deploy Hooks（同上） |

## 同じ environment を使う他のワークフロー

- `supabase_preview.yml`（Supabase Preview Branch）— `SUPABASE_MAIN_PROJECT_REF` や `VERCEL_TOKEN` 等を
  追加で必要とする。未設定なら警告を出して no-op で成功するため deploy の復旧には必須ではない。
  キー一覧と取得元は [Supabase PreviewブランチCI設計](20260717_1200_Supabase_PreviewブランチCI設計.md) の「必要な設定」を参照。
- `deploy_worker.yml`（Cloud Run の topic-analysis worker）— `GCP_PROJECT_ID` が未設定なら
  green でスキップする。staging で worker を動かすまでは登録不要。詳細は
  [トピック分析CloudRunプロビジョニング手順](20260609_1230_トピック分析CloudRunプロビジョニング手順.md) を参照。

## 登録コマンド

値は対話入力させ、シェル履歴に残さない。

```bash
for key in SUPABASE_ACCESS_TOKEN SUPABASE_PROJECT_REF SUPABASE_DB_PASSWORD \
           SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET \
           ADMIN_AUTH_CALLBACK_URL WEB_VERCEL_DEPLOY_HOOK_URL ADMIN_VERCEL_DEPLOY_HOOK_URL; do
  gh secret set "$key" --env staging -R codeforjapan/saga-broadlistening
done
```

登録済みキーの一覧（値は表示されない）:

```bash
gh api repos/codeforjapan/saga-broadlistening/environments/staging/secrets --jq '.secrets[].name'
```

## 検証方法

1. 上記コマンドで8件を登録し、一覧コマンドですべて表示されることを確認する
2. `develop` へ push する（または `gh run rerun <run-id>` で直近の失敗 run を再実行する）
3. `Migrate DB then Deploy` が `Check required secrets` → `Supabase link` → `Supabase db push`
   → `Trigger Vercel Deploy Hook` まで通り、成功することを確認する
4. Vercel の web / admin で `develop` のデプロイが起動していることを確認する

登録漏れがある状態では、`Check required secrets` が
`environment 'staging' に次の secret が未設定です: ...` と不足キーを列挙して落ちる。
