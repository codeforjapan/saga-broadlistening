# AIモデルと請求照合の運用

Issue #43。先行PR #118〜#122、#124の複数プロバイダー対応を前提とする。

## 接続先とモデルを選ぶ

既定はBedrock。`AI_ALLOWED_PROVIDERS`で`bedrock,gateway,openai,google`から許可する接続先を指定する。本番を含め、配置先の運用方針に応じて切り替えられる。

| 保存・設定するID | 接続先 |
| --- | --- |
| `bedrock:jp.anthropic.claude-haiku-4-5-20251001-v1:0` | Amazon Bedrock |
| `gateway:openai/gpt-5.2` または既存の `openai/gpt-5.2` | Vercel AI Gateway |
| `openai:gpt-5.2` | OpenAI直接接続 |
| `google:gemini-3-flash` | Google直接接続 |

カタログは管理画面に表示する候補。API利用権限、各モデルの提供状況、構造化出力への適合性は別途実APIで確認する。カタログ外のIDやBedrockの推論プロファイルは環境変数で指定できる。未登録モデルの公開表示は「カスタムモデル」とし、AWSアカウントを含み得る内部IDを公開しない。

- 公開チャットは全体共通、インタビューは意見募集ごとにモデルを保存する。
- 「環境の既定モデル」は固定のモデルIDを保存せず、用途別の`AI_*_MODEL` → `AI_DEFAULT_MODEL` → コードの既定値の順で解決する。既定値が許可外なら別の接続先へ自動フォールバックせずエラーとする。
- インタビュー、公開チャット、シミュレーション、意見再抽出のモデル候補は同じ許可プロバイダー設定に従う。サーバーでも許可外の接続先を拒否する。web/admin/workerの環境変数は自動同期されないため、各実行環境の許可リストと認証設定を揃える。現行CDKのworkerはBedrockに設定されており、他の接続先で再抽出を行う場合はworker側の設定変更も必要。
- 同じ名前のモデルでも、Gatewayと直接接続は異なるID・API認証・料金設定として扱う。
- 公開チャットとインタビューの料金が不明なら保存時・推論開始前に拒否する。確認した単価を`AI_MODEL_PRICING`へ設定する。未知の料金を0円と扱わない。

`AI_MODEL_PRICING`は既存の設定。新しい環境変数やDBマイグレーションはない。例の単価は導入先で公式料金を確認してから設定する。

```json
{
  "openai:gpt-5.2": {
    "inputTokensPerMillionUsd": 1.75,
    "outputTokensPerMillionUsd": 14
  }
}
```

単価はUSD / 100万tokens。概算の表示にも同じ上書き設定を使う。管理画面の円表示は入力85,000・出力3,000tokens、1 USD = 150円の固定仮定であり、実際の会話や為替を保証しない。

## 月次照合

担当は**システム運用担当者**。毎月、前月分を確認し、請求データが未確定なら確定後に再確認する。担当者は実行日、対象環境、対象期間、対象AWSアカウント・プロバイダー、集計値、差額、説明と対応をIssue #43または運用記録に残す。初回は #47 の検証実行で発生した使用量を用いる。

### 1. 比較する範囲を揃える

1. 開始日時を含み終了日時を含まないUTCの期間を決める。以下は2026年8月分の例。
2. stagingとproduction、AWSアカウント、接続先を分ける。Gateway経由のClaude料金をAWS Bedrockの請求に足さない。
3. `chat_usage_events`は公開チャット・インタビュー分。adminの評価・シミュレーション、worker分は含まない。これらはLangfuseの`functionId`別記録などから別途集計する。
4. Langfuseとアプリが同じ単価を使って一致しても、請求照合の代わりにはならない。プロバイダー側の使用量・請求明細と比較する。

### 2. アプリの記録を集計する

対象環境のSupabase SQL Editorで読み取り専用の集計を実行する。本文・個人情報は抽出しない。接続先を含む`model`ごとの集計を維持する。

```sql
select
  model,
  prompt_name,
  count(*) as requests,
  sum(input_tokens) as input_tokens,
  sum(output_tokens) as output_tokens,
  sum(cost_usd) as estimated_cost_usd
from public.chat_usage_events
where occurred_at >= timestamptz '2026-08-01 00:00:00+00'
  and occurred_at <  timestamptz '2026-09-01 00:00:00+00'
group by model, prompt_name
order by model, prompt_name;
```

過去の`provider/model`形式はGatewayとして集計する。入力・出力トークンを単価表で再計算し、1件ずつ保存した際の小数6桁丸めによる差も考慮する。

### 3. AWSの実請求を取得する

AWS Cost Explorerで同じ期間・アカウントのサービス、使用タイプ、リージョン別金額を確認し、請求明細へ遡ってモデルと対応付ける。Claudeの公式価格は`AmazonBedrockFoundationModels`でMarketplace software usageとして公開されているため、表示上の「Amazon Bedrock」だけに絞って必要な明細を取りこぼさないこと。Bedrock関連の請求項目を実データで特定してから絞り込む。

CLIを使う場合の読み取り専用例。Cost ExplorerのAPI利用料金・権限はAWS側の契約に従う。プロファイルと期間は対象環境に合わせる。

```bash
aws ce get-cost-and-usage \
  --profile saga-koucho-dev \
  --region us-east-1 \
  --time-period Start=2026-08-01,End=2026-09-01 \
  --granularity DAILY \
  --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=SERVICE Type=DIMENSION,Key=USAGE_TYPE \
  --output json > /tmp/ai-cost-2026-08.json
```

モデル別に特定できなければCost and Usage Reportや請求明細を併用する。JP CRISの実行先、請求リージョン、モデルを実際の明細で確認する。全アカウント分の金額を取得する例なので、関係しないサービスの費用は除外する。請求明細全体を公開リポジトリへ添付しない。

### 4. Gateway・直接接続の実請求を取得する

Gateway、OpenAI、Googleそれぞれの使用量・請求画面で同じ期間・プロジェクトの入力、出力、キャッシュ、ツール料金を確認する。アプリはGatewayの実費メタデータがあれば優先するが、請求画面の確定額との照合は別途行う。

### 5. 差額を説明し、必要なら修正する

比較対象は「アプリに記録したweb分＋admin/worker等の対象使用分」と「同じ範囲のプロバイダー請求」。税・クレジット・割引など比較範囲外の項目は分離して記録する。必ず請求額がアプリの概算以上になるとは限らない。

差額の原因を次の順で確認する。

- 対象期間・UTC/JST・請求反映遅延・環境・アカウント・モデル・接続先の不一致
- web以外の実行、再試行、途中失敗などによる課金と記録の差
- 単価、標準/Batch等の推論方式、キャッシュ読込/書込、長文入力帯の割増
- Web検索ツール等の追加料金、税、クレジット、個別契約

現行のトークン単価表はキャッシュ料金を分離していない。キャッシュや長文割増を利用する場合は現行の概算で実費が一致するとみなさず、計上ロジック・単価の対応を追加する。理由不明の差額や予算判定への影響はIssueに記録し、単価・記録漏れを修正して再検算する。

## 初回の実API検証

ローカルまたはstagingで実施する。本番の料金制限を検証用に変更しない。

1. 許可プロバイダーごとに管理画面の候補を確認。Bedrockのみなら3モデル、直接接続・Gateway併用なら接続先別に表示されること。
2. インタビューでモデルを選び保存し、再読込と情報開示の表示名を確認。未指定の場合は`AI_INTERVIEW_MODEL`などで解決した実モデルが表示されること。現行の`interview_configs.chat_model`はNOT NULLのため、未指定は空文字で保存する。公開チャット設定の未指定はNULLであり、保存形式が異なる。
3. 対象モデルでインタビューを1本通す。`chat_usage_events`のトークン・費用とLangfuseの実行モデル・使用量を確認。構造化出力・ツール適合性は #47 の検証と合わせる。
4. stagingの`CHAT_DAILY_USER_COST_LIMIT_USD`を検証用の小さい値へ一時変更し、制限に到達した利用者の次回リクエストが`DAILY_COST_LIMIT_REACHED`となることを確認する。事前に記録した設定へ必ず戻す。
5. 請求への反映後、上の手順で初回検算を実施する。実測値と結果を記録して初めて完了とする。

### 2026-09-18の確認結果

- AWS SSO再認証後、共通レジストリ経由の短いリクエストでHaiku 4.5とGPT OSS 120Bの応答・使用量を取得。Sonnet 4.6はAnthropic利用目的申請が未提出というエラーで失敗。
- Haikuはインタビュー画面からの通常・ストリーム呼び出しでも同じ申請エラーが発生した。CLI成功だけで全経路の利用可能性を保証しない。
- GPT OSSではローカルの実インタビュー対話と構造化レポート生成が成功。`chat_usage_events`の実入力/出力から再計算し、保存された料金と一致した。例: 入力3,133・出力257tokens → 0.000752 USD、入力3,172・出力2,083tokens → 0.002092 USD。小数6桁へ丸めた値。
- GPT OSSの初回質問生成ではスキーマ不適合も1件発生。対話・レポートの成功と、全工程の安定動作は区別し、#47で継続検証する。
- ローカルwebプロセスだけ日次上限を0.000001 USDに設定し、実使用量を記録した利用者の次回リクエストがHTTP 429・`DAILY_COST_LIMIT_REACHED`となることを確認。検証後にプロセスを停止し、一時設定を解除した。
- 管理画面で、許可外providerの更新拒否、直接接続の料金未設定時の新規作成・更新拒否、明示料金を設定した直接接続モデルの保存成功を実DBで確認。
- Cost Explorerで2026-09-15のGPT OSS利用分を確認。入力0.144K tokens = 0.00002592 USD、出力0.061K tokens = 0.00004453 USDで、東京単価0.18/0.73 USD per 1M tokensと一致した。取得時点では`Estimated=true`。これは過去利用分の単価検算であり、今回のアプリ記録や #47 のまとまった検証実費との突合ではない。
- ローカルのLangfuseキーは未設定のため、Langfuse generationとの照合は未実施。今回のリクエストは請求への反映を待って同期間・同範囲で照合する。

単価の公式照合と一部の実費単価検算は完了。全モデルの実インタビュー検証、Langfuse使用量との照合、#47の検証実費とアプリ記録の初回突合は未完了。手順書の作成や単体テストを初回突合の代わりにしない。
